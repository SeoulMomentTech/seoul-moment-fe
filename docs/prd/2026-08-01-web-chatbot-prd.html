작성일 2026-08-01 최종 갱신 2026-08-04 대상 앱 apps/web 상태 구현 완료 (UI + API 연동)

모든 페이지 우측 하단에 상시 노출되는 챗봇 진입점을 도입하기 위한 요구사항과 결정 항목입니다. 확정된 것과 논의가 필요한 것을 분리해 적었습니다.

이 페이지 오른쪽 아래 버튼은 실제로 동작하는 프로토타입입니다. 눌러서 패널을 열고, 스크롤해도 버튼이 유지되는지 확인해보세요. 패널 형태와 상태는 §5 프로토타입에서 바꿀 수 있습니다.

0이 문서를 읽는 방법

D-1 ~ D-9가 모두 결정되었습니다. 각 항목은 결정 내용이 첫 줄에 있고, 선택 근거로 옵션 비교를 아래에 남겨 두었습니다. F-n은 처음부터 확정된 요구사항입니다.

2026-08-06 응답 확장

PRODUCT_LIST tag와 상품을 담는 products 필드가 추가되었습니다({ id, name, brandName, price, image }). 브랜드·카테고리 안내를 넘어 개별 상품으로 안내하는 첫 단계로, D-1의 쇼핑 어시스턴트 확장에 한 발 더 다가갑니다. 브랜드·카테고리 목록(brands/categories)이 이름만 링크로 노출하는 것과 달리, products는 브랜드명·가격을 함께 보여주는 전용 UI로 렌더하고 각 항목은 /product/{id} 상세로 이동합니다(§5.3, §7.4). 오른쪽 아래 프로토타입의 PRODUCT_LIST 상태에서 직접 확인할 수 있습니다.

서비스 코드는 apps/web/src/shared/services/aiConsult.ts에 이미 생성되어 있습니다.

결정은 모두 끝났고 UI·API 연동까지 구현했습니다. 무엇이 되었고 무엇이 남았는지는 §13에 정리했습니다. 남은 것은 서버측 로그 적재 세부(D-7의 7-2)와 약관 수정입니다.

기술 구조(§7)에 적힌 내용은 실제 코드를 확인한 뒤 작성한 것으로, 인용된 파일 경로는 모두 현재 존재합니다.

1배경

Seoul Moment 웹은 상품·브랜드·매거진·뉴스·프로모션이 함께 놓인 콘텐츠 커머스입니다. 현재 사용자가 도움을 요청할 수 있는 창구는 /contact 문의 폼 하나뿐이고, 이는 비동기이며 사용자가 스스로 찾아 들어가야 합니다.

챗봇은 모든 페이지에서 즉시 닿는 단일 진입점을 만듭니다. 1차 역할은 CS·FAQ 응대로 정했습니다(D-1). 배송·교환·환불·회원 정책처럼 답이 이미 문서로 존재하는 질문을 사용자가 정책 페이지를 뒤지지 않고 해결하게 합니다. 상품 추천(쇼핑 어시스턴트)은 정확도가 확보된 뒤 확장합니다.

2목표

D-1이 CS·FAQ로 확정되었으므로 목표를 그 기준으로 적습니다.

  • 자기해결: 배송·교환·환불·회원 정책 질문을 사용자가 정책 페이지를 읽지 않고 챗봇 안에서 끝낸다.
  • 접근성: 어느 페이지에 있든 도움을 요청할 창구가 한 번의 클릭 안에 있다.
  • 연속성: 페이지를 이동해도 대화가 끊기지 않는다.
  • 막다른 길 없음: 챗봇이 답하지 못하는 질문에도 다음 행동이 항상 제시된다(D-5).
정성 목표

“무엇을 물어봐야 할지 모르겠다”는 상태를 만들지 않는다. 최초 진입 화면이 챗봇의 역할을 스스로 설명해야 합니다(D-8).

범위 경계: 상품 추천·재고 조회·주문 상태 확인은 1차 범위가 아닙니다. 사용자가 물으면 OFF_TOPIC으로 안내하고(§5.3), 어떤 질문이 실제로 많이 들어오는지는 D-7의 운영 로그로 확인해 확장 시점을 판단합니다.

3사용자와 시나리오

주 사용자: 비로그인 방문자. 현재 서비스는 로그인 없이도 상품·콘텐츠 전체를 볼 수 있고, 챗봇도 로그인 없이 사용합니다(F-4). 다수 사용자가 비로그인이므로 운영 로그(D-7)에도 비로그인 사용자의 대화가 대부분을 차지합니다 — 로그 설계를 계정 기준으로 잡으면 실제 데이터의 소수만 담깁니다.

우선 시나리오 (D-1 = CS·FAQ)

  1. 배송이 언제 오는지 알고 싶은 방문자 — “대만까지 며칠 걸려요?”
  2. 교환·환불 가능 여부와 조건을 확인하려는 방문자
  3. 회원 혜택·적립·쿠폰 조건을 묻는 방문자
  4. 문의 폼을 쓰기 전 “이걸 물어봐도 되나” 확인하려는 방문자

후순위 (쇼핑 어시스턴트 확장 시)

  1. 조건을 말로 설명해 상품을 찾고 싶은 방문자 — “선물용 20만원대 스킨케어 있어?”
  2. 매거진을 읽다 관련 브랜드로 넘어가고 싶은 방문자

5·6번 질문이 실제로 얼마나 들어오는지는 운영 로그(D-7)로 확인해 확장 시점을 판단합니다.

4확정 요구사항

F-1. 모든 페이지에 우측 하단 플로팅 버튼 상시 노출 확정

[locale] 하위 전 라우트(홈, 상품, 브랜드, 매거진, 뉴스, 프로모션, 마이페이지, 약관·정책, 로그인·가입, 404·에러 화면 포함)에서 화면 우측 하단에 플로팅 버튼이 보입니다.

노출 예외는 없습니다(D-6). 로그인·가입·정책·약관 화면에도 그대로 노출합니다.

우측 하단은 이미 점유되어 있어 자리 정리가 선행됩니다

Sonner 토스트를 하단 중앙으로 옮기고 ScrollToTop을 챗봇 버튼 위로 쌓습니다(D-9). 상세는 §7.2.

F-2. 라우트 이동 시 버튼·패널 상태 유지 확정

클라이언트 라우팅으로 페이지를 이동해도 버튼이 사라지거나 다시 나타나지 않습니다. 깜빡임(remount flash)도 없어야 합니다.

패널이 열린 상태에서 사용자가 페이지를 이동한 경우: 패널은 열린 채로 유지되고 대화 내용도 그대로 남습니다. 챗봇이 안내한 링크를 눌러 이동했을 때 대화가 끊기면 안내 자체가 무의미해지므로, 이는 F-2에 포함되는 확정 요구사항입니다.

F-3. 버튼 클릭 시 채팅 패널 오픈 확정

버튼을 누르면 챗봇과 대화할 수 있는 패널이 열립니다. 열린 상태에서 다시 누르면 닫힙니다. 패널의 형태·크기는 D-3에서 결정합니다.

F-4. 비로그인 사용 허용 확정

로그인 여부와 무관하게 누구나 챗봇을 사용합니다. 미로그인 사용자를 로그인 화면으로 보내거나 기능을 제한하지 않습니다.

대화는 세션 한정입니다(D-7). 로그인 여부와 무관하게 이력을 복원하지 않으며, 브라우저에도 남기지 않습니다.

  • 라우트 이동 중에도, 패널을 닫고 다시 열어도 대화는 유지됩니다. 이것은 저장이 아니라 클라이언트 메모리 상태의 연속성입니다(F-2).
  • 새로고침·탭 종료 시 대화가 사라집니다. 다시 열면 최초 진입 상태이며 이전 방문의 대화는 복원되지 않습니다.
  • 단, 대화는 운영 로그로 서버에 보관됩니다(D-7). 사용자 기능이 아니라 방향 논의용이며, 그래서 개인정보 검토가 여전히 필요합니다(§6).
  • 로그인 사용자 개인화(주문 내역 기반 응답 등)는 이번 범위 밖입니다(§9).

  • 입력 중 자동 높이 확장(최대 5줄), 이후 내부 스크롤.
  • 전송 중에는 전송 버튼만 비활성하고 입력은 계속 가능하게 합니다. 단발 응답(D-4)이므로 중지 버튼은 두지 않습니다. 취소할 스트림이 없고, 응답을 버리는 버튼은 기대를 잘못 만듭니다.
  • 입력 길이는 2~300자입니다. 서버가 이 범위를 벗어나면 400으로 거절하므로 전송 전에 클라이언트에서 막습니다. 300자 초과 시 카운터를 경고색으로, 2자 미달이면 전송 버튼을 비활성합니다.
  • 300자는 짧은 편이라 카운터를 240자 정도부터 미리 보여주는 편이 낫습니다. 다 쓰고 나서 막히면 다시 줄여야 합니다.

메시지 리스트 세부

  • 새 메시지 도착 시 자동 하단 스크롤. 단 사용자가 위로 스크롤해 과거 대화를 보는 중이면 자동 스크롤하지 않고 “새 메시지” 버튼을 띄웁니다.
  • 응답은 순수 텍스트입니다. answer는 문자열 하나이고 스키마에 링크·이미지 필드가 없습니다. 상품 카드·콘텐츠 카드는 물론 서버가 지정하는 링크도 없습니다.
  • 링크는 두 종류입니다.
    • /contact 문의 링크 — 답변 불가·범위 밖·장애일 때 프론트가 tag를 보고 붙입니다(D-5).
    • 브랜드·카테고리 링크 목록 — 서버가 brands·categories로 내려준 항목을 링크로 만듭니다. 목적지 매핑은 §7.4.
  • image는 카드가 아니라 행 앞 썸네일로 씁니다. 36×36 정사각 타일에 object-contain으로 담고, image가 없으면 썸네일만 빠집니다.
    • 카드로 만들지 않은 이유: 브랜드 이미지는 이름이 박힌 워드마크 로고라서(dev 실측 8개 중 7개) 카드 캡션과 이름이 중복되고, 비율이 1:1 다섯 개·약 2:1 세 개로 섞여 고정 비율 박스에서 레터박싱이 커집니다. 배경색(검정·연두·청록)도 이미지에 박혀 있어 패널 배경과 충돌합니다.
    • 대분류(CATEGORY_LIST)는 image가 3/3 모두 null입니다. 카드 그리드로 가면 같은 자리에서 태그별로 레이아웃이 갈리는데, 행 + 썸네일은 이미지가 없으면 그대로 텍스트 행이 되어 한 형태로 수렴합니다.
    • 타일에 크기를 주고 이미지는 max-h-full max-w-full로 담습니다. Tailwind preflight의 img { height: auto }가 next/image의 height를 덮어써서, 이미지에만 맡기면 행 높이가 원본 비율대로 들쭉날쭉해집니다.
    • 리치 카드를 만들지 않는다는 결정(§9)은 유지됩니다. 썸네일은 답변을 카드로 바꾸는 것이 아니라 링크 행의 식별을 돕는 장치입니다.
  • 목록은 5개까지만 접어서 노출하고, 그보다 많으면 목록 안에서 펼칩니다. 실제 응답은 브랜드 8개·소분류 9개를 주는데 전부 세로로 나열하면 좁은 패널에서 목록이 대화를 밀어냅니다. 마지막 행이 나머지 N개 보기(펼침 시 접기) 버튼이고, 누르면 이동 없이 그 자리에서 전부 열립니다.
  • 목록 페이지로 보내지 않습니다. 브랜드 목록 화면이 아직 없습니다 — app/[locale]/brand/page.tsx는 빈 화면에 robots: noindex가 걸린 플레이스홀더입니다. /product에도 브랜드 전체를 훑을 진입점이 없습니다(brandId는 단일 브랜드 필터). 빈 페이지로 보내는 링크는 없는 것보다 나쁘므로 제자리 펼치기를 택했습니다. 세 태그가 같은 자리에서 같은 동작을 하는 것도 이 방식의 이점입니다.
  • 펼치기 버튼은 링크가 아니라 버튼입니다. aria-expanded로 상태를 노출하고, 항목 링크의 >와 구분되도록 ⌄/⌃ 아이콘을 씁니다.
  • 목록 박스 폭은 답변 버블과 맞춥니다. 내용 길이에 맞춰 좁아지면 버블과 좌우 정렬이 어긋나 두 블록이 서로 다른 요소처럼 보입니다.
  • 목록과 되묻기 칩은 다르게 보여야 합니다. 칩은 “누르면 그 문구를 다시 질문”, 목록은 “누르면 그 페이지로 이동”입니다. 동작이 다르므로 칩(pill)과 링크 목록(세로 나열 + 화살표)을 시각적으로 구분합니다.
  • 되묻기 칩: 응답의 suggestions가 비어 있지 않으면 답변 아래에 칩으로 노출합니다(CONFIRM_SUGGESTION·OFF_TOPIC에서 관찰됨). 누르면 그 문구를 그대로 새 질문으로 보냅니다. 링크가 아니라 버튼입니다.
  • 링크·칩은 클릭 대상임이 분명해야 하므로 일반 텍스트와 확실히 구분하고(밑줄 또는 브랜드 컬러), 모바일에서 터치 가능한 높이를 확보합니다.

웰컴 메시지

  • 대화가 시작된 뒤에도 맨 위에 남깁니다. 개인정보 안내와 “창을 닫으면 사라져요”는 대화 중에도 유효한 정보이고, 챗봇의 역할 설명이 남아 있으면 범위 밖 질문도 줄어듭니다.
  • 대화 목록의 첫 항목으로 남기는 방식이므로 대화가 길어지면 위로 스크롤해야 보입니다. 상시 고정(sticky)은 좁은 팝오버에서 대화 영역을 계속 잠식해 채택하지 않았습니다.

배경 딤 · 스크롤 잠금 · 스크롤 체이닝

  • 팝오버(데스크톱): 딤 없음, 배경 스크롤 잠그지 않음. 페이지를 읽으며 대화하는 것이 이 형태의 목적입니다.
  • 전체화면(모바일): 딤 + 배경 스크롤 잠금. 잠그지 않으면 뒤 콘텐츠가 스크롤돼 어느 것이 활성인지 모호해집니다. 딤 클릭으로 닫힙니다.
  • 메시지 리스트와 입력창 모두 overscroll-contain을 적용해, 끝에 닿았을 때 스크롤이 배경 페이지로 전파되지 않게 합니다.
프로토타입에서 발견한 것

브랜드 오렌지 원색 #f37b2a는 흰 배경에서 본문 대비 4.5:1을 넘지 못합니다. 링크와 칩 텍스트에는 어둡게 조정한 톤(#b44e00 수준)이 필요하고, 원색은 버튼 배경처럼 면으로 쓸 때만 적합합니다. 구현 시 링크 색을 별도 토큰으로 두는 것을 권합니다.

5.3 상태 명세

응답 상태는 tag가 결정합니다. 레이트리밋·장애까지 200으로 내려오므로, HTTP 에러로 처리되는 상태와 tag로 처리되는 상태를 구분해야 합니다. 이 구분을 놓치면 장애 응답이 정상 답변처럼 화면에 남습니다.

목록도 배열 유무로 판단합니다

brands·categories는 해당 tag가 아니면 빈 배열로 오므로, tag로 분기하지 않고 length > 0이면 렌더합니다. suggestions와 같은 규칙입니다.

칩 렌더 기준은 tag가 아니라 suggestions 유무입니다

dev 서버 확인 결과 OFF_TOPIC에도 칩이 함께 옵니다. tag로 칩 노출을 분기하면 이런 경우를 놓치므로, suggestions.length > 0이면 렌더하는 편이 안전합니다.

5.4 접근성

  • 패널 오픈 시 포커스를 패널 내부로 이동, 내부에서 포커스 트랩. Esc로 닫고 닫을 때 포커스를 버튼으로 복귀.
  • 메시지 영역 aria-live="polite"로 새 응답을 스크린리더에 전달. 단발 응답이므로 완료 시점에 한 번 읽히면 됩니다(D-4).
  • 키보드만으로 열기 → 입력 → 전송 → 링크 이동 → 닫기 전 과정 가능.
  • 브랜드 오렌지 위 흰색 아이콘의 대비비를 실측 확인(오렌지 #f37b2a는 흰 텍스트 대비가 낮은 편이므로 아이콘 두께·크기로 보완).
  • 모션은 prefers-reduced-motion 사용자 설정을 따릅니다. 프로젝트에 reducedMotion="user"로 설정된 src/shared/ui/motion-provider.tsx가 이미 있습니다.

5.5 반응형

프로젝트는 모바일 퍼스트이며 sm(640px) 단일 경계를 씁니다.

  • 모바일(≤640px): 패널은 화면을 거의 다 차지합니다. 패널이 열려 있는 동안 플로팅 버튼은 숨기거나 패널 헤더의 닫기 버튼으로 대체합니다(작은 화면에서 버튼과 패널이 겹치는 것을 피하기 위함).
  • 데스크톱(>640px): 패널이 우측 하단에 뜨고 버튼은 그대로 보입니다.

6비기능 요구

성능

  • 챗봇은 전 페이지에 마운트되므로 초기 번들 증가가 전 라우트에 과금됩니다. 패널 본체와 대화 로직은 버튼 클릭 시점에 동적 로드하고, 초기 로드에는 버튼만 포함합니다.

  • 플로팅 버튼은 레이아웃 시프트를 만들지 않아야 합니다(fixed 요소이므로 CLS 영향 없음이 기대되나 실측 확인).

주의 — “저장하지 않음”은 사용자 기능에 관한 말입니다

D-7이 “사용자 이력 복원 없음”으로 정해졌지만 대화는 운영 로그로 서버에 쌓입니다. 사용자에게 복원 기능을 주지 않는 것과 서버에 저장하지 않는 것은 다릅니다. 개인정보 검토는 사라지지 않고, 오히려 사용자가 인지하지 못하는 저장이라 더 조심해야 합니다.

  • 로그도 개인정보입니다. 대화 원문에는 이름·주문번호·연락처가 사용자 손으로 입력될 수 있습니다. 보관 기간·파기 절차·접근 권한이 정의되어야 합니다(D-7의 7-2).
  • 고지 의무를 확인해야 합니다. 사용자는 화면에서 대화가 사라지므로 서버에 남는다고 인지하지 못합니다. 개인정보 처리방침에 챗봇 대화 로그 항목을 명시할지 법무 확인이 필요합니다.
  • 삭제 요청 대응 경로가 필요합니다. 로그가 계정에 귀속되지 않으면(익명 세션 ID) 특정 사용자의 대화를 찾아 지우는 것이 불가능에 가깝습니다. 이 점을 7-2에서 감안해야 합니다.
  • 입력 유도: 사용자가 개인정보를 입력하지 않도록 웰컴 메시지에 안내를 넣습니다. 저장이 없다고 오해하게 만드는 문구는 쓰지 않습니다.
  • LLM 제공자 전송: 자체 백엔드를 거쳐(D-2) LLM에 전달되므로 제3자 제공 해당 여부를 검토해야 합니다.
  • 로그 접근 통제: 운영 로그는 방향 논의용이므로 열람 권한을 최소 인원으로 제한하고 접근 기록을 남깁니다.
  • 화면에 대화 삭제 버튼을 두지 않습니다. 창을 닫거나 새로고침하면 대화가 사라지므로 별도 버튼이 필요하지 않고, “삭제” 버튼은 서버 로그까지 지워진다는 오해를 만듭니다. 로그 삭제 요청은 D-7의 7-2 경로로 처리합니다.

에러 관측

  • 프로젝트는 Sentry가 붙어 있고 5xx 응답은 beforeError 훅에서 자동 리포트됩니다. 챗봇 API 실패도 같은 경로를 탑니다.

구현 시 반드시 지킬 것 다섯 가지
  1. tag로 분기해야 합니다. 레이트리밋·LLM 장애가 200으로 내려오므로 useAppMutation의 onError를 타지 않습니다. onSuccess 안에서 tag를 보고 화면을 갈라야 하고, 이걸 놓치면 장애 응답이 정상 답변처럼 보입니다(§5.3).
  2. 문맥을 보내지 않습니다. 요청 본문은 { message } 하나뿐이고 서버가 이전 대화를 기억하지 않습니다. 이전 메시지를 모아 보내려는 시도는 스펙에 없습니다.
  3. 400 응답의 message는 문자열이 아니라 검증 객체 배열입니다. 전역 MutationCache.onError가 message를 토스트에 쓰므로, toastOnError: false가 아니면 객체가 토스트에 들어갑니다. 애초에 길이는 클라이언트에서 막아 400이 나지 않게 합니다.
  4. languageCode는 POST에서 자동 변환되지 않습니다. index.ts의 beforeRequest 훅이 GET만 처리하므로(if (method === "GET")), askAiConsult는 Accept-language 헤더를 직접 설정합니다. 서비스 파일에 주석으로 남겨 두었습니다.
  5. suggestions 조회는 마운트 시점이 아니라 오픈 시점입니다. 위젯이 전 페이지에 마운트되므로 마운트 시 조회하면 챗봇을 열지 않는 대다수에게도 요청이 나갑니다(§6 성능 요구 위반). enabled: isOpen으로 처리하고, 실패해도 패널 렌더를 막지 않습니다.

useQuery/useMutation 직접 사용은 ESLint로 금지되어 있으므로 반드시 래퍼(src/shared/lib/hooks/query/)를 씁니다. 챗봇 에러는 전역 토스트가 아니라 패널 내부에서 처리하므로 toastOnError: false가 맞습니다.

상태 관리: D-7에 따라 단순합니다.

  • 패널 열림 + 대화 상태: zustand. 기존 스토어(src/shared/lib/hooks/useModal.ts, useUserAuthStore.ts)와 같은 방식. 이 메모리 상태만으로 F-2(라우트 이동 중 유지)가 충족됩니다.
  • persist 미들웨어를 쓰지 않습니다. 브라우저에 대화를 남기지 않는 것이 D-7의 결정이므로 순수 메모리 상태여야 합니다.
  • 메시지에 tag를 함께 보관합니다. 응답 렌더가 tag에 따라 달라지므로(§5.3) 화면 상태를 다시 만들 수 있게 메시지 단위로 들고 있어야 합니다.
  • 스토어가 들고 있는 것: isOpen, messages, languageCode(언어 변경 감지 기준), rateLimitedUntil(차단 해제 시각).
  • 언어 변경 감지 기준을 스토어에 둡니다. 컴포넌트 useRef 로 비교하면 [locale] 세그먼트가 바뀔 때 런처가 리마운트되어 ref 가 새 언어로 초기화되고, “바뀌었다”를 영영 감지하지 못합니다. 실제로 이 방식으로 먼저 구현했다가 초기화가 전혀 동작하지 않아 스토어로 옮겼습니다.
  • 레이트리밋 차단 시간은 60초이며 useChatbotConversation 의 RATE_LIMIT_BLOCK_MS 상수입니다. 서버가 남은 시간을 내려주게 되면 이 상수만 교체합니다.
  • 로그아웃 시 처리: GlobalQueryHandler가 로그아웃 시 쿼리를 비웁니다. 챗봇 대화 상태도 같은 시점에 초기화해야 합니다.

B. CS·FAQ 응대범위가 좁아 정확도 확보 쉬움. 지식베이스가 정책·약관 페이지로 이미 존재매출 기여를 증명하기 어려움. 문의량이 적으면 효과 미미
C. 콘텐츠 큐레이션매거진·뉴스·룩북 자산 활용. 브랜드 톤과 잘 맞음효과가 간접적. 사용자가 챗봇에 기대하는 역할과 어긋날 수 있음
선택 근거 (B → A)

범위가 좁아 첫 버전의 정확도를 확보할 수 있고, 정책·약관·FAQ라는 지식베이스가 이미 문서 형태로 존재합니다. A는 오답 비용이 크고 카탈로그 검색 인프라가 선행되어야 합니다.

확장 판단 기준: 상품·콘텐츠 관련 질문이 운영 로그(D-7)에서 유의미하게 관찰되면 A로 확장을 검토합니다.

D-2. 응답 엔진 결정

결정

자체 백엔드 API + LLM. 프론트는 자체 백엔드와만 통신하고, LLM 호출·레이트 리밋은 백엔드가 담당합니다. 서드파티 위젯은 채택하지 않습니다.

스펙 확인 결과 LLM의 역할이 좁습니다. 답변 문장은 서버에 사전 정의된 상수이고, LLM은 질문을 FAQ 지식과 의미 기반으로 매칭하는 데만 쓰입니다. 답변을 생성하지 않으므로 환각(없는 정책을 만들어내는 오답)의 위험이 낮습니다. 대신 위험이 “엉뚱한 FAQ를 매칭하는 것”으로 옮겨갑니다.

따라오는 것

  • 백엔드에 대화 전송 엔드포인트와 운영 로그 적재가 필요합니다(§7.4).
  • 멀티턴 문맥이 없습니다. 서버가 이전 대화를 기억하지 않으므로 합의할 것도 없습니다. 화면에는 대화가 쌓이지만 각 질문은 독립 처리됩니다(§5.2).
  • FAQ 지식·답변 상수 구성은 이 문서 범위 밖이며 백엔드·기획이 별도로 정합니다(§9). 답변 문구 품질이 곧 챗봇 품질이므로 이쪽 비중이 큽니다.
  • D-1의 쇼핑 어시스턴트 확장은 이 구조로는 안 됩니다. 사전 정의 답변으로는 상품 추천을 할 수 없어, 확장 시 카탈로그 검색과 생성형 응답이 새로 필요합니다.
  • 목업 단계는 건너뛰었습니다 — 스펙과 dev 서버가 이미 준비되어 있어 처음부터 실제 API에 붙였습니다(§13).

7-1. 확정된 것과 그 함의

구분결정

이 결정의 실질적 의미를 오해하지 말아야 합니다. “저장하지 않음”은 사용자 기능에 관한 말이고, 서버에는 대화가 쌓입니다. 따라서 다음이 여전히 필요합니다.

  • 개인정보 처리방침 검토. 사용자가 화면에서 대화가 사라지는 것을 보고 “기록이 없다”고 이해할 수 있어, 고지 필요성을 법무가 판단해야 합니다.
  • 보관 기간과 파기 절차, 로그 접근 권한 통제(§6).
  • 로그에 개인정보가 섞여 들어오는 것에 대한 대비. 사용자가 이름·주문번호·연락처를 입력할 수 있습니다.

얻는 것: 프론트 구현이 가장 단순해지고(이력 조회·삭제 API 없음, persist 없음), Phase 1을 백엔드 이력 기능 없이 완결할 수 있습니다. 나중에 사용자 이력 복원을 도입하더라도 버릴 코드가 없습니다.

포기하는 것: 사용자가 대화를 이어갈 수 없습니다. CS·FAQ는 한 번에 끝나는 질문이 많아 손실이 크지 않지만, 긴 상담이 끊기면 처음부터 다시 물어야 합니다. 로그에서 “같은 사용자가 반복 질문하는 패턴”이 관찰되면 이력 복원 도입을 재검토합니다.

  • 칩 내용은 하드코딩이 아니라 GET /ai-consult/suggestions에서 받아옵니다. 문구를 배포 없이 조정할 수 있다는 뜻이므로, 운영 로그(D-7)로 확인한 질문 패턴을 칩에 반영하는 루프가 성립합니다.
  • 칩은 두 곳에 나옵니다: 최초 진입(suggestions API)과 응답 후 되묻기(CONFIRM_SUGGESTION의 suggestions). 같은 컴포넌트로 처리하고 출처만 다릅니다(§5.3).
  • 버튼 자체는 아무 유도도 하지 않습니다(§5.1의 미읽음 표시 없음).
  • 조회 실패 시 칩 없이 시작하되 직접 입력은 그대로 동작해야 합니다(§5.3).

(1) 토스트 — position="bottom-center"

변경 지점: apps/web/src/app/[locale]/layout.tsx의 <Toaster />에 position="bottom-center"를 추가합니다. 현재 옵션 없이 마운트되어 기본값(bottom-right)이 적용된 상태입니다.

  • 전 페이지 영향입니다. 성공·실패 토스트 위치가 모두 바뀌므로 QA 범위에 기존 토스트 노출 지점(로그인, 마이페이지 저장, 관심상품 등)을 포함해야 합니다.
  • 하단 중앙은 챗봇 버튼과 완전히 분리되고 모바일에서도 읽기 편합니다.

(2) ScrollToTop — 챗봇 버튼 위 세로 스택

변경 지점: apps/web/src/views/promotion/ui/PromotionPage.tsx의 <ScrollToTop className="bottom-20 right-[5%] ..." />. 우측 정렬을 챗봇 버튼과 같은 축(right: 24px)으로 맞추고, bottom을 챗봇 버튼(56px) 위 8~12px로 조정합니다.

  • 두 버튼이 하나의 스택으로 읽히도록 우측 축을 맞추는 것이 핵심입니다. right-[5%]는 뷰포트 폭에 따라 축이 흔들립니다.
  • 크기도 함께 볼 필요가 있습니다. 현재 size-10(40px)이고 챗봇 버튼은 56px이라 축을 맞춰도 시각적으로 어긋납니다. 같은 크기로 맞추거나 의도적으로 위계를 두되 중앙축은 정렬합니다.
  • 모바일 확인 필요: 두 버튼이 세로로 쌓이면 작은 화면에서 높이를 잡아먹습니다. 프로모션 페이지 모바일에서 실기기 확인이 필요합니다.

Phase 3에서 필요하다고 판단된 것. 스트리밍은 D-4에서 도입하지 않기로 했으므로, 응답 지연이 실제 이탈 요인으로 확인될 때만 재검토합니다.

구현 중 확인된 것

  • OFF_TOPIC 에도 suggestions 가 온다: dev 서버 실측. 그래서 칩 노출은 tag 가 아니라 배열 유무로 판단한다(§5.2).
  • 400 응답의 message 는 검증 객체 배열: 문자열이 아니다. toastOnError: false 가 아니면 객체가 토스트에 들어간다.
  • languageCode 는 POST 에서 자동 변환되지 않는다: 훅이 GET 만 처리하므로 헤더를 직접 넣는다.
  • 답변은 서버 상수: LLM 은 의미 매칭만 한다. 환각 위험은 낮고 오매칭 위험이 남는다.
  • 대분류와 소분류는 쿼리 파라미터가 다르다: categoryId vs productCategoryId. 같은 이름으로 보내면 필터가 걸리지 않는다(§7.4).
  • 목록 응답이 길다: dev 실측으로 브랜드 8개, 패션 소분류 9개다. 전부 나열하면 답변 한 건이 패널을 넘겨서 5개로 잘랐다(§5.2).
  • 브랜드 목록 화면이 없다: app/[locale]/brand/page.tsx는 빈 noindex 플레이스홀더다. “전체 보기” 링크를 걸면 빈 페이지로 보내게 되므로 제자리 펼치기로 바꿨다(§5.2).
  • image가 태그마다 다르다: dev 실측으로 브랜드 8/8, 소분류 9/9 는 있고 대분류는 3/3 모두 null이다. 카드 그리드가 아니라 행 썸네일을 택한 이유다(§5.2).
  • 브랜드 이미지는 워드마크 로고다: 8개 중 7개가 브랜드명을 이미지로 렌더한 것이고 배경색이 박혀 있다. 비율도 1:1 과 2:1 로 섞여 있어 object-cover로 채우면 잘린다.
  • Tailwind preflight 가 next/image의 height 를 덮어쓴다: img { height: auto } 때문에 크기를 이미지가 아니라 감싼 타일에 줘야 행 높이가 고정된다.

다음 단계

프론트 구현은 끝났습니다. 남은 것은 대부분 프론트 밖입니다(§13).

  1. 서버측 운영 로그 적재를 확인합니다. 프론트는 POST /ai-consult/ask 만 호출하고 로그에 관여하지 않으므로, 실제로 쌓이고 있는지 백엔드와 맞춰야 합니다.
  2. 7-2의 로그 정책을 확정하고 약관·처리방침 수정을 법무에 요청합니다. 대화가 서버에 남는다는 사실을 고지할지가 여기서 결정됩니다.
  3. QA 범위에 토스트 위치 변경을 포함합니다: 전 페이지 영향입니다(로그인·마이페이지 저장·관심상품 등).
  4. 프로모션 페이지를 데이터가 있는 환경에서 확인합니다: ScrollToTop 스택이 모바일에서 화면 높이를 잡아먹지 않는지.
  5. 로그가 쌓이면 Phase 3(§10)로 넘어가 7-3의 네 가지를 판단합니다.
