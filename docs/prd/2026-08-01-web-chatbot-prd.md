## 0. 이 문서를 읽는 방법

**D-1 ~ D-9가 모두 결정되었습니다.** 각 항목은 결정 내용이 첫 줄에 있고, 선택 근거로 옵션 비교를 아래에 남겨 두었습니다. **F-n**은 처음부터 확정된 요구사항입니다.

### 결정 현황

| 항목 | 결정 |
| --- | --- |
| D-1 챗봇의 1차 목적 | CS·FAQ 위주로 시작, 추후 쇼핑 어시스턴트로 확장 |
| D-2 응답 엔진 | 자체 백엔드 API + LLM |
| D-3 패널 형태 | A. 버튼 앵커 팝오버 |
| D-4 스트리밍 응답 | **단발 응답 + 로딩 인디케이터** (스트리밍 미도입) |
| D-5 에스컬레이션 | **`/contact` 문의 폼으로 유도** |
| D-6 노출 예외 페이지 | **예외 없음** — 전 라우트 노출 |
| D-7 대화 이력 저장 | 사용자 이력 복원 없음 + 운영 로그로만 서버 보관. **약관·처리방침 수정 진행** |
| D-8 최초 진입 유도 | **추천 질문 칩만** — 자동 툴팁·미읽음 뱃지 없음 |
| D-9 우측 하단 자리 정리 | **(1) 토스트 `position="bottom-center"` / (2) ScrollToTop을 챗봇 버튼 위 세로 스택** |

### 확정된 API

| 메서드 | 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| `POST` | `/ai-consult/ask` | `{ message }` (2~300자) | `{ answer, tag, suggestions }` |
| `GET` | `/ai-consult/suggestions` | 없음 | `{ total, list: string[] }` |

스펙에서 확인된 세 가지가 이 문서 전체에 영향을 줍니다.

1. **이전 대화를 기억하지 않습니다.** 매 질문이 독립적이고 서버에 문맥이 없습니다.
2. **레이트리밋·장애도 200으로 내려옵니다.** `tag` 값으로 분기해야 하며 HTTP 에러 경로를 타지 않습니다.
3. **답변은 서버 상수입니다.** LLM은 의미 기반 검색만 하고 답변 문장을 생성하지 않습니다.

`tag`는 `FAQ_ANSWER` · `CONFIRM_SUGGESTION` · `FALLBACK` · `OFF_TOPIC` · `RATE_LIMITED` · `UNAVAILABLE` 여섯 가지입니다(§5.3).

서비스 코드는 `apps/web/src/shared/services/aiConsult.ts`에 이미 생성되어 있습니다.

**결정은 모두 끝났고 UI·API 연동까지 구현했습니다.** 무엇이 되었고 무엇이 남았는지는 §13에 정리했습니다. 남은 것은 서버측 로그 적재 세부(D-7의 7-2)와 약관 수정입니다.

기술 구조(§7)에 적힌 내용은 실제 코드를 확인한 뒤 작성한 것으로, 인용된 파일 경로는 모두 현재 존재합니다.

## 1. 배경

Seoul Moment 웹은 상품·브랜드·매거진·뉴스·프로모션이 함께 놓인 콘텐츠 커머스입니다. 현재 사용자가 도움을 요청할 수 있는 창구는 `/contact` 문의 폼 하나뿐이고, 이는 비동기이며 사용자가 스스로 찾아 들어가야 합니다.

챗봇은 **모든 페이지에서 즉시 닿는 단일 진입점**을 만듭니다. 1차 역할은 **CS·FAQ 응대**로 정했습니다(D-1). 배송·교환·환불·회원 정책처럼 답이 이미 문서로 존재하는 질문을 사용자가 정책 페이지를 뒤지지 않고 해결하게 합니다. 상품 추천(쇼핑 어시스턴트)은 정확도가 확보된 뒤 확장합니다.

---

## 2. 목표

D-1이 CS·FAQ로 확정되었으므로 목표를 그 기준으로 적습니다.

- **자기해결**: 배송·교환·환불·회원 정책 질문을 사용자가 정책 페이지를 읽지 않고 챗봇 안에서 끝낸다.
- **접근성**: 어느 페이지에 있든 도움을 요청할 창구가 **한 번의 클릭 안에** 있다.
- **연속성**: 페이지를 이동해도 대화가 끊기지 않는다.
- **막다른 길 없음**: 챗봇이 답하지 못하는 질문에도 다음 행동이 항상 제시된다(D-5).

**정성 목표**: "무엇을 물어봐야 할지 모르겠다"는 상태를 만들지 않는다. 최초 진입 화면이 챗봇의 역할을 스스로 설명해야 합니다(D-8).

**범위 경계**: 상품 추천·재고 조회·주문 상태 확인은 1차 범위가 아닙니다. 사용자가 물으면 `OFF_TOPIC`으로 안내하고(§5.3), 어떤 질문이 실제로 많이 들어오는지는 D-7의 운영 로그로 확인해 확장 시점을 판단합니다.

---

## 3. 사용자와 시나리오

**주 사용자**: 비로그인 방문자. 현재 서비스는 로그인 없이도 상품·콘텐츠 전체를 볼 수 있고, 챗봇도 로그인 없이 사용합니다(F-4). 다수 사용자가 비로그인이므로 **운영 로그(D-7)에도 비로그인 사용자의 대화가 대부분을 차지합니다** — 로그 설계를 계정 기준으로 잡으면 실제 데이터의 소수만 담깁니다.

**우선 시나리오** (D-1 = CS·FAQ)

1. 배송이 언제 오는지 알고 싶은 방문자 — "대만까지 며칠 걸려요?"
2. 교환·환불 가능 여부와 조건을 확인하려는 방문자
3. 회원 혜택·적립·쿠폰 조건을 묻는 방문자
4. 문의 폼을 쓰기 전 "이걸 물어봐도 되나" 확인하려는 방문자

**후순위** (쇼핑 어시스턴트 확장 시)

5. 조건을 말로 설명해 상품을 찾고 싶은 방문자 — "선물용 20만원대 스킨케어 있어?"
6. 매거진을 읽다 관련 브랜드로 넘어가고 싶은 방문자

5·6번 질문이 실제로 얼마나 들어오는지는 운영 로그(D-7)로 확인해 확장 시점을 판단합니다.

## 4. 확정 요구사항

### F-1. 모든 페이지에 우측 하단 플로팅 버튼 상시 노출

`[locale]` 하위 전 라우트(홈, 상품, 브랜드, 매거진, 뉴스, 프로모션, 마이페이지, 약관·정책, 로그인·가입, 404·에러 화면 포함)에서 화면 **우측 하단**에 플로팅 버튼이 보입니다.

**노출 예외는 없습니다**(D-6). 로그인·가입·정책·약관 화면에도 그대로 노출합니다.

**우측 하단은 이미 점유되어 있어 자리 정리가 선행됩니다.** Sonner 토스트를 하단 중앙으로 옮기고 `ScrollToTop`을 챗봇 버튼 위로 쌓습니다(D-9). 상세는 §7.2.

### F-2. 라우트 이동 시 버튼·패널 상태 유지

클라이언트 라우팅으로 페이지를 이동해도 버튼이 사라지거나 다시 나타나지 않습니다. 깜빡임(remount flash)도 없어야 합니다.

**패널이 열린 상태에서 사용자가 페이지를 이동한 경우**: 패널은 열린 채로 유지되고 대화 내용도 그대로 남습니다. 챗봇이 안내한 링크를 눌러 이동했을 때 대화가 끊기면 안내 자체가 무의미해지므로, 이는 F-2에 포함되는 확정 요구사항입니다.

### F-3. 버튼 클릭 시 채팅 패널 오픈

버튼을 누르면 챗봇과 대화할 수 있는 패널이 열립니다. 열린 상태에서 다시 누르면 닫힙니다. 패널의 형태·크기는 **D-3**에서 결정합니다.

### F-4. 비로그인 사용 허용

로그인 여부와 무관하게 누구나 챗봇을 사용합니다. 미로그인 사용자를 로그인 화면으로 보내거나 기능을 제한하지 않습니다.

**대화는 세션 한정입니다**(D-7). 로그인 여부와 무관하게 이력을 복원하지 않으며, 브라우저에도 남기지 않습니다.

- 라우트 이동 중에도, 패널을 닫고 다시 열어도 대화는 유지됩니다. 이것은 *저장*이 아니라 클라이언트 메모리 상태의 연속성입니다(F-2).
- **새로고침·탭 종료 시 대화가 사라집니다.** 다시 열면 최초 진입 상태이며 이전 방문의 대화는 복원되지 않습니다.
- 단, **대화는 운영 로그로 서버에 보관됩니다**(D-7). 사용자 기능이 아니라 방향 논의용이며, 그래서 개인정보 검토가 여전히 필요합니다(§6).
- 로그인 사용자 개인화(주문 내역 기반 응답 등)는 이번 범위 밖입니다(§9).

## 5. 화면 · 인터랙션 명세

### 5.1 플로팅 버튼

| 항목 | 명세 |
| --- | --- |
| 위치 | 화면 우측 하단 고정. 데스크톱 `right: 24px / bottom: 24px`, 모바일 `right: 16px / bottom: 16px` (제안값) |
| 크기 | 데스크톱 56px, 모바일 48px 원형 (터치 타깃 최소 44px 충족) |
| 색상 | 브랜드 오렌지 `brand #f37b2a` 배경 + 흰색 아이콘 |
| 아이콘 | 닫힘 상태 말풍선, 열림 상태 X (`lucide-react` 사용) |
| 그림자 | 기존 `ScrollToTop`의 소프트 섀도 톤을 따름 |
| 레이블 | `aria-label` 필수. 아이콘만으로는 스크린리더 대응 불가 |
| 전환 | 아이콘 회전·크로스페이드 `duration-normal`(200ms). `prefers-reduced-motion` 시 즉시 전환 |
| 미읽음 표시 | **없음**(D-8). 자동 툴팁·뱃지를 띄우지 않고, 유도는 패널 안 추천 질문 칩으로만 합니다 |

### 5.2 패널 구조

형태는 팝오버로 확정(D-3). 구조는 3단입니다.

```
┌─────────────────────────────┐
│ 헤더  제목 · 닫기              │
├─────────────────────────────┤
│                             │
│ 메시지 리스트 (스크롤)         │
│  - 봇 메시지 / 사용자 메시지    │
│  - 추천 질문 칩               │
│  - 인라인 링크(상품·콘텐츠)     │
│                             │
├─────────────────────────────┤
│ 입력부  textarea · 전송 버튼    │
└─────────────────────────────┘
```

**입력부 세부**

- Enter 전송, Shift+Enter 줄바꿈. 모바일에서는 전송 버튼 탭이 기본.
- **각 질문은 독립적으로 처리됩니다**(스펙: 이전 대화를 기억하지 않음). "그거 말고", "그럼 얼마예요?" 같은 지시적 질문은 답을 얻지 못합니다. placeholder와 웰컴 문구로 자기완결적 질문을 유도합니다.
- 입력 중 자동 높이 확장(최대 5줄), 이후 내부 스크롤.
- **전송 중에는 전송 버튼만 비활성**하고 입력은 계속 가능하게 합니다. 단발 응답(D-4)이므로 중지 버튼은 두지 않습니다. 취소할 스트림이 없고, 응답을 버리는 버튼은 기대를 잘못 만듭니다.
- **입력 길이는 2~300자입니다.** 서버가 이 범위를 벗어나면 400으로 거절하므로 전송 전에 클라이언트에서 막습니다. 300자 초과 시 카운터를 경고색으로, 2자 미달이면 전송 버튼을 비활성합니다.
- 300자는 짧은 편이라 카운터를 240자 정도부터 미리 보여주는 편이 낫습니다. 다 쓰고 나서 막히면 다시 줄여야 합니다.

**메시지 리스트 세부**

- 새 메시지 도착 시 자동 하단 스크롤. 단 사용자가 위로 스크롤해 과거 대화를 보는 중이면 자동 스크롤하지 않고 "새 메시지" 버튼을 띄웁니다.
- **응답은 순수 텍스트입니다.** `answer`는 문자열 하나이고 스키마에 링크·이미지 필드가 없습니다. 상품 카드·콘텐츠 카드는 물론 서버가 지정하는 링크도 없습니다.
- **화면에 나타나는 링크는 프론트가 붙이는 것 하나뿐입니다** — 답변 불가·범위 밖·장애일 때의 `/contact` 문의 링크(D-5). `tag`를 보고 프론트가 판단해 붙입니다.
- **되묻기 칩**: 응답의 `suggestions`가 비어 있지 않으면 답변 아래에 칩으로 노출합니다(`CONFIRM_SUGGESTION`·`OFF_TOPIC`에서 관찰됨). 누르면 그 문구를 그대로 새 질문으로 보냅니다. 링크가 아니라 버튼입니다.
- 링크·칩은 클릭 대상임이 분명해야 하므로 일반 텍스트와 확실히 구분하고(밑줄 또는 브랜드 컬러), 모바일에서 터치 가능한 높이를 확보합니다.

**웰컴 메시지**

- 대화가 시작된 뒤에도 **맨 위에 남깁니다.** 개인정보 안내와 "창을 닫으면 사라져요"는 대화 중에도 유효한 정보이고, 챗봇의 역할 설명이 남아 있으면 범위 밖 질문도 줄어듭니다.
- 대화 목록의 첫 항목으로 남기는 방식이므로 대화가 길어지면 위로 스크롤해야 보입니다. 상시 고정(sticky)은 좁은 팝오버에서 대화 영역을 계속 잠식해 채택하지 않았습니다.

**스크롤 체이닝**

- 메시지 리스트와 입력창 모두 `overscroll-contain`을 적용해, 끝에 닿았을 때 스크롤이 배경 페이지로 전파되지 않게 합니다.

**배경 딤과 스크롤 잠금**

D-3 형태에 따라 갈리며, 형태 결정과 함께 정해야 합니다.

- **팝오버(A)**: 딤 없음, 배경 스크롤 잠그지 않음. 페이지를 읽으며 대화하는 것이 이 형태의 목적입니다.
- **사이드 시트(B) · 전체화면(C)**: 모달 성격이므로 딤 + 배경 스크롤 잠금이 필요합니다. 잠그지 않으면 뒤 콘텐츠가 스크롤돼 어느 것이 활성인지 모호해집니다.
- 딤을 쓰는 형태에서는 딤 클릭으로 닫히는 동작을 함께 제공합니다.

### 5.3 상태 명세

**응답 상태는 `tag`가 결정합니다.** 레이트리밋·장애까지 200으로 내려오므로, HTTP 에러로 처리되는 상태와 `tag`로 처리되는 상태를 구분해야 합니다. 이 구분을 놓치면 장애 응답이 정상 답변처럼 화면에 남습니다.

#### `tag`별 화면 (모두 HTTP 200)

| `tag` | 의미 | 화면 |
| --- | --- | --- |
| `FAQ_ANSWER` | 답변 찾음 | `answer` 텍스트만. `suggestions`는 보통 빈 배열 |
| `CONFIRM_SUGGESTION` | 답이 애매해 되물음 | `answer` + **되묻기 칩**(`suggestions`). 누르면 그 문구를 새 질문으로 전송 |
| `FALLBACK` | 답변 불가 | `answer` + **`/contact` 문의 링크**(D-5). 프론트가 붙입니다 |
| `OFF_TOPIC` | 쇼핑몰 무관 질문 거절 | `answer` + **되묻기 칩**. dev 서버 확인 결과 이 `tag`에도 `suggestions`가 채워져 옵니다. 1차 범위 밖 질문(상품 추천·주문 조회)도 여기로 옵니다 |
| `RATE_LIMITED` | 요청 제한 | `answer` + 입력부 위 배너에 남은 시간 카운트다운. **전송만 차단하고 입력·타이핑은 유지**. 차단 시간은 60초 — 응답 스키마에 대기 시간 필드가 없어 클라이언트가 정한 값이다(§7.4) |
| `UNAVAILABLE` | LLM 장애 | `answer` + 재시도 안내 + `/contact` 링크. **정상 답변처럼 보이지 않게** 시각적으로 구분 |

`answer`는 어떤 `tag`에서도 항상 채워져 옵니다(서버 상수). 프론트가 문구를 따로 만들 필요는 없고, 문구 위에 무엇을 덧붙일지만 `tag`로 정합니다.

**칩 렌더 기준은 `tag`가 아니라 `suggestions` 유무입니다.** dev 서버 확인 결과 `OFF_TOPIC`에도 칩이 함께 옵니다. `tag`로 칩 노출을 분기하면 이런 경우를 놓치므로, `suggestions.length > 0`이면 렌더하는 편이 안전합니다.

#### 그 밖의 상태

| 상태 | 화면 |
| --- | --- |
| 최초 진입 | 웰컴 메시지 + 추천 질문 칩. **새 방문·새로고침 후 처음 열 때 이 상태입니다** — 이전 방문의 대화를 복원하지 않습니다(D-7) |
| 첫 질문 이후 | **웰컴 메시지는 맨 위에 남고, 최초 진입 칩만 사라집니다.** 이미 질문을 시작한 사용자에게 "무엇을 물어볼까" 목록은 방해입니다. 응답에 딸려 오는 되묻기 칩은 별개이므로 계속 노출합니다 |
| **언어 변경** | 대화를 비우고 추천 질문을 새 언어로 다시 조회합니다. 서버가 `Accept-language`에 따라 답변 언어를 바꾸므로 초기화하지 않으면 한 대화에 두 언어가 섞입니다. 패널은 열린 채로 유지됩니다 |
| 추천 질문 로딩 중 | `GET /ai-consult/suggestions` 응답 대기. 칩 자리에 스켈레톤을 두고 웰컴 메시지는 먼저 보여줍니다 |
| 추천 질문 조회 실패 | 칩 없이 웰컴 메시지 + 입력창만. **패널을 못 쓰게 만들지 않습니다** — 직접 입력은 그대로 동작해야 합니다 |
| 전송 중 | 사용자 메시지 즉시 표시(낙관적) + 봇 영역에 로딩 인디케이터. 단발 응답이므로 중지 버튼 없음(D-4) |
| **네트워크·서버 오류** | HTTP 에러(네트워크 끊김, 5xx, 타임아웃)일 때만 이 상태. 실패한 메시지 옆 인라인 에러 + 재시도 버튼. 전역 토스트로 띄우지 않음 |
| 입력 길이 미달 | 2자 미만이면 전송 버튼 비활성. 별도 메시지 없이 버튼 상태로만 알림 |
| 입력 길이 초과 | 300자 초과 시 카운터 경고 + 전송 차단. 240자쯤부터 카운터를 미리 노출 |
| 오프라인 | 입력부 위 배너 "네트워크 연결을 확인해주세요". 온라인 복귀 시 자동 제거 |
| 긴 대화 | 메시지 100건 초과 시 오래된 메시지 접기 또는 가상화 |
| 패널 닫고 다시 열기 | 대화가 그대로 남아 있고 하단으로 스크롤된 상태. 실수로 닫는 경우를 고려한 것이며 저장이 아니라 메모리 유지입니다(D-7) |
| 새로고침 후 | 대화가 사라지고 최초 진입 상태. **닫기 시점에 소멸을 경고하지 않습니다** — 세션 한정임을 웰컴 문구에서 이미 전제하고, 닫을 때마다 경고를 띄우면 마찰만 커집니다 |

### 5.4 접근성

- 패널 오픈 시 포커스를 패널 내부로 이동, 내부에서 포커스 트랩. Esc로 닫고 닫을 때 포커스를 버튼으로 복귀.
- 메시지 영역 `aria-live="polite"`로 새 응답을 스크린리더에 전달. 단발 응답이므로 완료 시점에 한 번 읽히면 됩니다(D-4).
- 키보드만으로 열기 → 입력 → 전송 → 링크 이동 → 닫기 전 과정 가능.
- 브랜드 오렌지 위 흰색 아이콘의 대비비를 실측 확인(오렌지 `#f37b2a`는 흰 텍스트 대비가 낮은 편이므로 아이콘 두께·크기로 보완).
- 모션은 `prefers-reduced-motion` 사용자 설정을 따릅니다. 프로젝트에 `reducedMotion="user"`로 설정된 `src/shared/ui/motion-provider.tsx`가 이미 있습니다.

### 5.5 반응형

프로젝트는 모바일 퍼스트이며 `sm`(640px) 단일 경계를 씁니다.

- **모바일(≤640px)**: 패널은 화면을 거의 다 차지합니다. 패널이 열려 있는 동안 플로팅 버튼은 숨기거나 패널 헤더의 닫기 버튼으로 대체합니다(작은 화면에서 버튼과 패널이 겹치는 것을 피하기 위함).
- **데스크톱(>640px)**: 패널이 우측 하단에 뜨고 버튼은 그대로 보입니다.

## 6. 비기능 요구

**성능**

- 챗봇은 전 페이지에 마운트되므로 **초기 번들 증가가 전 라우트에 과금됩니다.** 패널 본체와 대화 로직은 버튼 클릭 시점에 동적 로드하고, 초기 로드에는 버튼만 포함합니다.
- 챗봇 도입 전후로 홈·상품 상세의 LCP / INP를 비교해 회귀가 없음을 확인합니다.
- 플로팅 버튼은 레이아웃 시프트를 만들지 않아야 합니다(`fixed` 요소이므로 CLS 영향 없음이 기대되나 실측 확인).

**개인정보 · 보안**

> **주의**: D-7이 "사용자 이력 복원 없음"으로 정해졌지만 **대화는 운영 로그로 서버에 쌓입니다.** 사용자에게 복원 기능을 주지 않는 것과 서버에 저장하지 않는 것은 다릅니다. **개인정보 검토는 사라지지 않고, 오히려 사용자가 인지하지 못하는 저장이라 더 조심해야 합니다.**

- **로그도 개인정보입니다.** 대화 원문에는 이름·주문번호·연락처가 사용자 손으로 입력될 수 있습니다. 보관 기간·파기 절차·접근 권한이 정의되어야 합니다(D-7의 7-2).
- **고지 의무를 확인해야 합니다.** 사용자는 화면에서 대화가 사라지므로 서버에 남는다고 인지하지 못합니다. 개인정보 처리방침에 챗봇 대화 로그 항목을 명시할지 **법무 확인이 필요합니다.**
- **삭제 요청 대응 경로가 필요합니다.** 로그가 계정에 귀속되지 않으면(익명 세션 ID) 특정 사용자의 대화를 찾아 지우는 것이 불가능에 가깝습니다. 이 점을 7-2에서 감안해야 합니다.
- **입력 유도**: 사용자가 개인정보를 입력하지 않도록 웰컴 메시지에 안내를 넣습니다. 저장이 없다고 오해하게 만드는 문구는 쓰지 않습니다.
- **LLM 제공자 전송**: 자체 백엔드를 거쳐(D-2) LLM에 전달되므로 제3자 제공 해당 여부를 검토해야 합니다.
- **로그 접근 통제**: 운영 로그는 방향 논의용이므로 열람 권한을 최소 인원으로 제한하고 접근 기록을 남깁니다.
- **화면에 대화 삭제 버튼을 두지 않습니다.** 창을 닫거나 새로고침하면 대화가 사라지므로 별도 버튼이 필요하지 않고, "삭제" 버튼은 서버 로그까지 지워진다는 오해를 만듭니다. 로그 삭제 요청은 D-7의 7-2 경로로 처리합니다.

**에러 관측**

- 프로젝트는 Sentry가 붙어 있고 5xx 응답은 `beforeError` 훅에서 자동 리포트됩니다. 챗봇 API 실패도 같은 경로를 탑니다.

## 7. 기술 구조 제안

이 절은 구현 확정안이 아니라 **코드베이스 확인 결과에 기반한 제약과 권장 경로**입니다.

### 7.1 마운트 지점 — F-2를 만족하는 유일한 위치

`apps/web/src/app/[locale]/layout.tsx`가 유일한 루트 레이아웃입니다(`src/app/layout.tsx`는 존재하지 않습니다). 이 레이아웃 안, `<Header />`와 `<main>`의 **형제**로 마운트하면 클라이언트 라우팅 시 언마운트되지 않습니다.

```tsx
<ReactQueryProvider>
  <Header />
  <main>{children}</main>
  <Footer />
  <ChatbotLauncher />   {/* ← 여기 */}
</ReactQueryProvider>
```

**금지**: `views/*`, 개별 `page.tsx`, 또는 `contact/layout.tsx` 같은 중첩 레이아웃에 두면 라우트가 바뀔 때마다 재마운트되어 F-2를 위반합니다.

### 7.2 레이어(z-index)와 충돌 검토

현재 프로젝트의 레이어는 3단뿐입니다.

| 레이어 | 값 | 대상 |
| --- | --- | --- |
| 콘텐츠 | `z-1` ~ `z-11` | 일반 요소 |
| 헤더 | `z-11` | `fixed`, 높이 56px |
| 오버레이·포털 | `z-50` | Dialog / Drawer / Sheet / Select / DropdownMenu |

권장: **버튼 `z-40`** — 콘텐츠보다 위, 모달보다 아래. 상품 이미지 확대 모달이 열렸을 때 챗봇 버튼이 그 위에 뜨면 안 됩니다.

**충돌 점검 결과: 우측 하단은 이미 두 요소가 쓰고 있습니다.** F-1을 우측 하단으로 확정했으므로 자리 정리가 구현의 선행 조건입니다.

| 기존 요소 | 위치 | 범위 | 충돌 내용 |
| --- | --- | --- | --- |
| Sonner `Toaster` | 기본값 `bottom-right` (`src/app/[locale]/layout.tsx`에 옵션 없이 마운트) | **전 페이지** | 토스트가 챗봇 버튼 위에 겹쳐 뜹니다. sonner는 매우 높은 z-index를 쓰므로 토스트가 떠 있는 동안 **버튼 클릭이 막힙니다** |
| `ScrollToTop` | `bottom-20 right-[5%] z-50 size-10` (`src/views/promotion/ui/PromotionPage.tsx`) | 프로모션 페이지 | 같은 우측 하단 영역. 버튼 두 개가 세로로 근접해 오조작 위험 |

그 외에는 비어 있습니다. 모바일 하단 내비게이션, 쿠키 배너, 기존 채팅 위젯(Channel Talk 등)이 없고, 화면에 고정된 광고도 없습니다(AdSense는 모두 인플로우).

**해소 방법** (D-9에서 확정)

- **토스트**: `<Toaster position="bottom-center" />`로 변경. 전 페이지 영향이므로 기존 토스트 노출 지점을 QA 범위에 포함합니다.
- **ScrollToTop**: 우측 축을 챗봇 버튼과 맞추고(`right: 24px`) 챗봇 버튼 위 8~12px에 배치해 하나의 스택으로 정렬합니다.
- 두 조치 모두 **챗봇이 아닌 기존 컴포넌트를 수정합니다.** Phase 1 범위에 포함됩니다.

**남은 주의사항**: 데스크톱 헤더가 `min-w-[1280px]`를 강제해 1280px보다 좁은 뷰포트에서는 가로 스크롤바가 생깁니다. 또한 우측 하단은 **세로 스크롤바와 인접**하므로 버튼이 스크롤바를 덮거나 스크롤 조작을 방해하지 않는지 실기기 확인이 필요합니다.

### 7.3 FSD 배치 제안

프로젝트는 FSD를 쓰고 상위 레이어 import가 ESLint로 금지됩니다(`app → views → widgets → features → entities → shared`).

```
src/widgets/chatbot/
├─ index.tsx                              배럴 (ChatbotLauncher 만 노출)
├─ ui/
│   ├─ ChatbotLauncher.tsx                "use client" · 버튼 + 패널 동적 로드
│   ├─ ChatbotPanel.tsx                   패널 셸 (반응형 분기 · 포커스 트랩 · 스크롤 잠금)
│   ├─ ChatMessageList.tsx                웰컴 · 메시지 · 칩 · 로딩 · 새 메시지 버튼
│   ├─ ChatMessage.tsx                    tag 별 렌더(문의 링크 · 경고 스타일 · 되묻기 칩)
│   ├─ ChatComposer.tsx                   입력부 (2~300자 검증 · 자동 높이)
│   ├─ ChatSuggestions.tsx                추천 질문 칩 (최초 진입 · 되묻기 공용)
│   ├─ RateLimitBanner.tsx                레이트리밋 배너 + 카운트다운
│   └─ scrollbar.ts                       스크롤 영역 공통 스타일 상수
├─ model/
│   ├─ types.ts                           ChatbotMessage · CONTACT_LINK_TAGS · WARNING_TAGS
│   ├─ useChatbotStore.ts                 zustand (persist 없음)
│   ├─ useChatbotConversation.ts          전송 · 재시도 · tag 분기 · 레이트리밋 발동
│   └─ useResetChatbotOnLanguageChange.ts 언어 변경 시 초기화
└─ api/
    ├─ queryKey.ts                        쿼리 키 (조회·초기화가 공유)
    ├─ useAskAiConsultMutation.ts         POST /ai-consult/ask
    └─ useGetAiConsultSuggestionsQuery.ts GET  /ai-consult/suggestions
```

서비스 함수는 기존 관례대로 `src/shared/services/aiConsult.ts`에 둡니다(`api` ky 인스턴스 사용, `src/shared/services/index.ts`에 배럴 추가).

**네이밍**: 제품 명칭은 "챗봇"이지만 API 도메인은 `ai-consult`입니다. 서비스·훅 이름은 API를 따르고(`aiConsult`, `useAskAiConsultMutation`), 위젯·UI 컴포넌트는 화면 용어를 따릅니다(`widgets/chatbot`, `ChatbotPanel`). 팀이 한쪽으로 통일하고 싶다면 착수 전에 정해야 합니다.

D-7에 따라 **이력 조회·삭제 훅은 만들지 않습니다.** 운영 로그 적재는 `POST /ai-consult/ask` 안에서 서버가 처리하므로 프론트에 별도 호출이 없습니다. 프론트가 로그 전송을 따로 하면 사용자가 차단할 수 있고 실패 처리도 이중이 됩니다.

`widgets` 레이어가 맞습니다. 전역 셸 요소이며 특정 도메인에 묶이지 않고, 기존 `widgets/scroll-to-top`, `widgets/header`와 성격이 같습니다.

### 7.4 API 연동과 상태

**엔드포인트 두 개로 완결됩니다.** 서비스 함수는 `apps/web/src/shared/services/aiConsult.ts`에 생성되어 있습니다.

| 훅 | 호출 | 시점 | 비고 |
| --- | --- | --- | --- |
| `useGetAiConsultSuggestionsQuery` | `getAiConsultSuggestions` | **패널을 처음 열 때** | `useAppQuery` 래퍼. `staleTime` 기본 5분이므로 세션 중 재조회 없음 |
| `useAskAiConsultMutation` | `askAiConsult` | 메시지 전송 시 | `useAppMutation` 래퍼, `toastOnError: false` |

**구현 시 반드시 지킬 것 다섯 가지**

1. **`tag`로 분기해야 합니다.** 레이트리밋·LLM 장애가 200으로 내려오므로 `useAppMutation`의 `onError`를 타지 않습니다. `onSuccess` 안에서 `tag`를 보고 화면을 갈라야 하고, 이걸 놓치면 장애 응답이 정상 답변처럼 보입니다(§5.3).
2. **문맥을 보내지 않습니다.** 요청 본문은 `{ message }` 하나뿐이고 서버가 이전 대화를 기억하지 않습니다. 이전 메시지를 모아 보내려는 시도는 스펙에 없습니다.
3. **400 응답의 `message`는 문자열이 아니라 검증 객체 배열입니다.** 전역 `MutationCache.onError`가 `message`를 토스트에 쓰므로, `toastOnError: false`가 아니면 객체가 토스트에 들어갑니다. 애초에 길이는 클라이언트에서 막아 400이 나지 않게 합니다.
4. **`languageCode`는 POST에서 자동 변환되지 않습니다.** `index.ts`의 `beforeRequest` 훅이 GET만 처리하므로(`if (method === "GET")`), `askAiConsult`는 `Accept-language` 헤더를 직접 설정합니다. 서비스 파일에 주석으로 남겨 두었습니다.
5. **suggestions 조회는 마운트 시점이 아니라 오픈 시점입니다.** 위젯이 전 페이지에 마운트되므로 마운트 시 조회하면 챗봇을 열지 않는 대다수에게도 요청이 나갑니다(§6 성능 요구 위반). `enabled: isOpen`으로 처리하고, 실패해도 패널 렌더를 막지 않습니다.

`useQuery`/`useMutation` 직접 사용은 ESLint로 금지되어 있으므로 반드시 래퍼(`src/shared/lib/hooks/query/`)를 씁니다. 챗봇 에러는 전역 토스트가 아니라 패널 내부에서 처리하므로 `toastOnError: false`가 맞습니다.

**상태 관리** — D-7에 따라 단순합니다.

- **패널 열림 + 대화 상태**: zustand. 기존 스토어(`src/shared/lib/hooks/useModal.ts`, `useUserAuthStore.ts`)와 같은 방식. 이 메모리 상태만으로 F-2(라우트 이동 중 유지)가 충족됩니다.
- **`persist` 미들웨어를 쓰지 않습니다.** 브라우저에 대화를 남기지 않는 것이 D-7의 결정이므로 순수 메모리 상태여야 합니다. 덕분에 `useUserAuthStore`가 겪는 hydration 불일치 문제를 챗봇 스토어는 겪지 않습니다.
- **메시지에 `tag`를 함께 보관합니다.** 응답 렌더가 `tag`에 따라 달라지므로(§5.3) 화면 상태를 다시 만들 수 있게 메시지 단위로 들고 있어야 합니다.
- **스토어가 들고 있는 것**: `isOpen`, `messages`, `languageCode`(언어 변경 감지 기준), `rateLimitedUntil`(차단 해제 시각).
- **언어 변경 감지 기준을 스토어에 둡니다.** 컴포넌트 `useRef` 로 비교하면 `[locale]` 세그먼트가 바뀔 때 런처가 리마운트되어 ref 가 새 언어로 초기화되고, "바뀌었다"를 영영 감지하지 못합니다. 실제로 이 방식으로 먼저 구현했다가 초기화가 전혀 동작하지 않아 스토어로 옮겼습니다.
- **레이트리밋 차단 시간은 60초**이며 `useChatbotConversation`의 `RATE_LIMIT_BLOCK_MS` 상수입니다. 서버가 남은 시간을 내려주게 되면 이 상수만 교체합니다.
- **로그아웃 시 처리**: `GlobalQueryHandler`가 로그아웃 시 쿼리를 비웁니다. 챗봇 대화 상태도 같은 시점에 초기화해야 합니다. 그렇지 않으면 로그아웃 후에도 이전 사용자의 대화가 화면에 남습니다.

### 7.5 트랜스포트 — 기존 규약 그대로

D-4가 단발 응답으로 확정되어 **실시간 통신을 도입하지 않습니다.** `ky` 기반 기존 서비스 레이어(`src/shared/services/`, 베이스 `https://api.seoulmoment.com.tw`, `CommonRes<T>` 래핑)를 그대로 씁니다.

- 스트리밍용 `src/app/api/` Route Handler 프록시, Netlify 스트리밍 검증, SSE 도입은 **모두 불필요해졌습니다.**
- 대신 **단발 응답의 지연을 UI로 흡수해야 합니다**: LLM 응답은 3~5초가 걸릴 수 있으므로 로딩 인디케이터가 살아 있어야 하고, `ky` 기본 타임아웃 10초가 LLM 응답에 충분한지 확인해 필요하면 이 엔드포인트만 늘립니다.
- 응답이 길어질 때를 대비해 UI는 나중에 토큰 누적 렌더로 바꿀 수 있는 구조로 둡니다(메시지 텍스트를 통째로 교체 가능한 형태).

## 8. 결정 사항

### D-1. 챗봇의 1차 목적 ✅ 결정

> **결정: CS·FAQ 위주로 시작하고, 추후 쇼핑 어시스턴트로 확장합니다.**

아래 옵션 비교는 선택 근거로 남겨 둡니다.

| 옵션 | 장점 | 단점 |
| --- | --- | --- |
| **A. 쇼핑 어시스턴트** | 매출에 직접 연결. 상품 데이터가 이미 API로 존재 | 상품 카탈로그 임베딩·검색 인프라 필요. 오답 시 신뢰 손상이 큼 |
| **B. CS·FAQ 응대** | 범위가 좁아 정확도 확보 쉬움. 지식베이스가 정책·약관 페이지로 이미 존재 | 매출 기여를 증명하기 어려움. 문의량이 적으면 효과 미미 |
| **C. 콘텐츠 큐레이션** | 매거진·뉴스·룩북 자산 활용. 브랜드 톤과 잘 맞음 | 효과가 간접적. 사용자가 챗봇에 기대하는 역할과 어긋날 수 있음 |

**선택 근거(B → A)**: 범위가 좁아 첫 버전의 정확도를 확보할 수 있고, 정책·약관·FAQ라는 지식베이스가 이미 문서 형태로 존재합니다. A는 오답 비용이 크고 카탈로그 검색 인프라가 선행되어야 합니다.

**확장 판단 기준**: 상품·콘텐츠 관련 질문이 운영 로그(D-7)에서 유의미하게 관찰되면 A로 확장을 검토합니다. 확장에는 상품 카탈로그 검색 인프라가 선행되어야 합니다.

### D-2. 응답 엔진 ✅ 결정

> **결정: 자체 백엔드 API + LLM.**

프론트는 자체 백엔드와만 통신하고, LLM 호출·레이트 리밋은 백엔드가 담당합니다. 서드파티 위젯은 채택하지 않습니다.

**스펙 확인 결과 LLM의 역할이 좁습니다.** 답변 문장은 서버에 사전 정의된 상수이고, LLM은 질문을 FAQ 지식과 의미 기반으로 매칭하는 데만 쓰입니다. 답변을 생성하지 않으므로 **환각(없는 정책을 만들어내는 오답)의 위험이 낮습니다.** 대신 위험이 "엉뚱한 FAQ를 매칭하는 것"으로 옮겨갑니다.

**따라오는 것**
- 백엔드에 대화 전송 엔드포인트와 운영 로그 적재가 필요합니다(§7.4).
- **멀티턴 문맥이 없습니다.** 서버가 이전 대화를 기억하지 않으므로 합의할 것도 없습니다. 화면에는 대화가 쌓이지만 각 질문은 독립 처리됩니다(§5.2).
- 지식베이스(FAQ 지식과 답변 상수) 구성은 이 문서 범위 밖이며 백엔드·기획이 별도로 정합니다(§9). **답변 문구 품질이 곧 챗봇 품질**이므로 이쪽 비중이 큽니다.
- **D-1의 쇼핑 어시스턴트 확장은 이 구조로는 안 됩니다.** 사전 정의 답변으로는 상품 추천을 할 수 없어, 확장 시 카탈로그 검색과 생성형 응답이 새로 필요합니다.
- 목업 단계는 건너뛰었습니다 — 스펙과 dev 서버가 이미 준비되어 있어 처음부터 실제 API에 붙였습니다(§13).

아래 옵션 비교는 선택 근거로 남겨 둡니다.

| 옵션 | 장점 | 단점 |
| --- | --- | --- |
| **자체 백엔드 API + LLM** | UI·디자인 완전 통제, 데이터·프롬프트 통제, 서비스 데이터 연동 가능 | 백엔드 개발 필요, LLM 비용 관리·레이트 리밋 직접 구현 |
| **서드파티 위젯 (Channel Talk 등)** | 빠른 도입, 상담원 기능 포함. **대부분 우측 하단이 기본값이라 F-1 위치 요구와는 맞습니다** | 디자인·패널 형태 커스터마이즈가 제한적(D-3 선택이 좁아짐). 기존 우하단 요소와의 자리 정리(D-9)를 위젯 설정 범위 안에서 해결해야 함 |
| **프론트 목업 선행** | UI/UX와 F-1~F-4를 먼저 확정, 백엔드와 병렬 진행 | 목업 상태로는 사용자 검증 불가 |

**선택 근거**: 서드파티 위젯은 위치(우측 하단)가 기본값과 맞아 F-1과는 충돌하지 않지만, 패널 형태(D-3)와 상태 화면(§5.3)을 이 문서 수준으로 통제할 수 없습니다. 자체 구현은 개발 비용이 들지만 UI·데이터·프롬프트를 모두 통제할 수 있어 CS·FAQ 정확도를 직접 관리할 수 있습니다.

- 모바일은 전체화면이므로 딤·스크롤 잠금이 필요하고, `src/shared/ui/bottom-sheet.tsx`(vaul Drawer)를 재사용합니다.

### D-4. 스트리밍 응답 여부 ✅ 결정

> **결정: 단발 응답 + 로딩 인디케이터.** 스트리밍(SSE)은 도입하지 않습니다.

**따라오는 것**
- 실시간 통신 도입이 없어 `ky` 기존 규약을 그대로 씁니다(§7.5). Netlify 스트리밍 검증·Route Handler 프록시가 불필요해집니다.
- 중지 버튼을 두지 않습니다(§5.2). 취소할 스트림이 없습니다.
- **지연을 UI로 흡수해야 합니다**: LLM 응답 3~5초 동안 로딩 인디케이터가 살아 있어야 하고, `ky` 기본 타임아웃 10초가 충분한지 확인이 필요합니다.
- 스크린리더는 완료 시점에 한 번만 읽습니다(§5.4).

| 옵션 | 장점 | 단점 |

### D-5. 답변 불가 시 에스컬레이션 ✅ 결정

### D-7. 대화 이력 저장 정책 ✅ 결정

> **결정: 사용자 대상 이력 복원은 제공하지 않습니다.** 대화는 세션 한정이며 새로고침·탭 종료 시 사라집니다.

#### 7-1. 확정된 것과 그 함의

| | 결정 |
| --- | --- |
| 라우트 이동 중 | **유지**(F-2). 메모리 상태이며 저장이 아닙니다 |
| 패널 닫고 다시 열기 | **유지**. 실수로 닫았을 때 대화를 잃지 않아야 하므로 탭 세션 동안은 메모리에 남깁니다 |
| 새로고침 · 탭 종료 후 | **소멸**. 다시 열면 최초 진입 상태 |
| 브라우저 저장 | 없음. `localStorage`·`sessionStorage` 모두 사용하지 않음 |
| 서버 | **운영 로그로 보관** — 사용자에게 노출되지 않는 분석·개선용 |
| 로그인 여부 | 무관. 비로그인 대화도 로그 대상 |

**이 결정의 실질적 의미를 오해하지 말아야 합니다.** "저장하지 않음"은 *사용자 기능*에 관한 말이고, 서버에는 대화가 쌓입니다. 따라서 다음이 **여전히 필요합니다.**

- 개인정보 처리방침 검토. 사용자가 화면에서 대화가 사라지는 것을 보고 "기록이 없다"고 이해할 수 있어, 고지 필요성을 법무가 판단해야 합니다.
- 보관 기간과 파기 절차, 로그 접근 권한 통제(§6).
- 로그에 개인정보가 섞여 들어오는 것에 대한 대비. 사용자가 이름·주문번호·연락처를 입력할 수 있습니다.

**얻는 것**: 프론트 구현이 가장 단순해지고(이력 조회·삭제 API 없음, `persist` 없음), Phase 1을 백엔드 이력 기능 없이 완결할 수 있습니다. 나중에 사용자 이력 복원을 도입하더라도 버릴 코드가 없습니다.

**포기하는 것**: 사용자가 지난 대화를 다시 볼 수 없습니다. 다만 **서버가 애초에 문맥을 기억하지 않으므로**(스펙) 이력을 복원해도 "이어지는 상담"이 되지는 않습니다. 이력 복원의 가치는 "지난 답변을 다시 읽는 것"까지이고, 로그에서 반복 질문 패턴이 관찰되면 그때 재검토합니다.

### D-8. 최초 진입 유도 ✅ 결정

> **결정: 추천 질문 칩만.** 자동 툴팁·미읽음 뱃지를 띄우지 않습니다.

**따라오는 것**
- 칩 내용은 하드코딩이 아니라 **`GET /ai-consult/suggestions`에서 받아옵니다.** 문구를 배포 없이 조정할 수 있다는 뜻이므로, 운영 로그(D-7)로 확인한 질문 패턴을 칩에 반영하는 루프가 성립합니다.
- **칩은 두 곳에 나옵니다**: 최초 진입(suggestions API)과 응답 후 되묻기(`CONFIRM_SUGGESTION`의 `suggestions`). 같은 컴포넌트로 처리하고 출처만 다릅니다(§5.3).
- 버튼 자체는 아무 유도도 하지 않습니다(§5.1의 미읽음 표시 없음).
- 조회 실패 시 칩 없이 시작하되 직접 입력은 그대로 동작해야 합니다(§5.3).

아래 옵션 비교는 선택 근거로 남겨 둡니다.

| 옵션 | 설명 |
| --- | --- |
| **A. 자동 툴팁 · 미읽음 뱃지** | 첫 방문 후 N초 뒤 말풍선 자동 노출 |
| **B. 추천 질문 칩만** | 패널을 열었을 때만 안내. 밖에서는 조용함 |
| **C. 완전 수동** | 아무 유도 없음 |

**선택 근거**: 자동 툴팁은 초기 사용률을 올리지만 콘텐츠를 가리고 광고처럼 인식됩니다. 특히 모바일 우측 하단에서 자동으로 튀어나오면 오조작을 유발합니다. 사용률이 낮다면 A를 나중에 실험으로 추가할 수 있습니다.

### D-9. 우측 하단 자리 정리 ✅ 결정

> **결정 (1) 토스트**: Sonner `Toaster`를 `position="bottom-center"`로 변경합니다.
> **결정 (2) ScrollToTop**: 챗봇 버튼 위로 세로 스택 정렬합니다.

F-1이 우측 하단으로 확정되면서 기존 두 요소와 자리가 겹치던 문제를 이렇게 해소합니다(§7.2).

#### (1) 토스트 — `position="bottom-center"`

**변경 지점**: `apps/web/src/app/[locale]/layout.tsx`의 `<Toaster />`에 `position="bottom-center"`를 추가합니다. 현재 옵션 없이 마운트되어 기본값(`bottom-right`)이 적용된 상태입니다.

- **전 페이지 영향**입니다. 성공·실패 토스트 위치가 모두 바뀌므로 QA 범위에 기존 토스트 노출 지점(로그인, 마이페이지 저장, 관심상품 등)을 포함해야 합니다.
- 하단 중앙은 챗봇 버튼과 완전히 분리되고 모바일에서도 읽기 편합니다.

#### (2) ScrollToTop — 챗봇 버튼 위 세로 스택

**변경 지점**: `apps/web/src/views/promotion/ui/PromotionPage.tsx`의 `<ScrollToTop className="bottom-20 right-[5%] ..." />`. 우측 정렬을 챗봇 버튼과 같은 축(`right: 24px`)으로 맞추고, `bottom`을 챗봇 버튼(56px) 위 8~12px로 조정합니다.

- 두 버튼이 하나의 스택으로 읽히도록 우측 축을 맞추는 것이 핵심입니다. `right-[5%]`는 뷰포트 폭에 따라 축이 흔들립니다.
- 크기도 함께 볼 필요가 있습니다. 현재 `size-10`(40px)이고 챗봇 버튼은 56px이라 축을 맞춰도 시각적으로 어긋납니다. 같은 크기로 맞추거나 의도적으로 위계를 두되 중앙축은 정렬합니다.
- **모바일 확인 필요**: 두 버튼이 세로로 쌓이면 작은 화면에서 높이를 잡아먹습니다. 프로모션 페이지 모바일에서 실기기 확인이 필요합니다.

## 10. 릴리스 단계

**Phase 1 — UI 셸과 자리 정리** ✅ 완료

우하단 자리 정리(D-9: 토스트 위치 변경 + ScrollToTop 스택), 루트 레이아웃 마운트, 플로팅 버튼, 팝오버 패널(D-3), 상태 화면, 접근성, UI 문구. **F-1 ~ F-4가 여기서 완결되었습니다.**

D-9를 맨 앞에 둔 이유: 토스트가 챗봇 버튼 클릭을 막기 때문에, 자리 정리 전에는 버튼을 붙여도 제대로 테스트할 수 없습니다.

**Phase 2 — API 연동** ✅ 완료 (프론트)

`GET /ai-consult/suggestions`로 추천 질문 칩, `POST /ai-consult/ask`로 대화 처리. 목업을 건너뛰고 처음부터 실제 API에 붙였습니다 — 스펙과 dev 서버가 이미 준비되어 있어 목업이 불필요했습니다.

*남은 것*: 서버측 운영 로그 적재(D-7)와 7-2의 로그 정책, 약관·처리방침 수정. 프론트는 로그에 관여하지 않습니다(§7.4).

**Phase 3 — 로그 기반 방향 재논의** (대기)

일정 기간 로그를 관찰한 뒤 7-3의 네 가지를 판단합니다. 이력 복원 필요성, 쇼핑 어시스턴트 확장 시점, 지식베이스 공백, 추천 질문 재구성. **다음 단계는 여기서 나오는 결론이 정합니다.**

**Phase 4 — 고도화** (대기)

Phase 3에서 필요하다고 판단된 것. 스트리밍은 D-4에서 도입하지 않기로 했으므로, 응답 지연이 실제 이탈 요인으로 확인될 때만 재검토합니다.

### 구현 중 확인된 것

- **`OFF_TOPIC` 에도 `suggestions` 가 온다** — dev 서버 실측. 그래서 칩 노출은 `tag` 가 아니라 배열 유무로 판단한다(§5.2).
- **400 응답의 `message` 는 검증 객체 배열** — 문자열이 아니다. `toastOnError: false` 가 아니면 객체가 토스트에 들어간다.
- **`languageCode` 는 POST 에서 자동 변환되지 않는다** — 훅이 GET 만 처리하므로 헤더를 직접 넣는다.
- **답변은 서버 상수** — LLM 은 의미 매칭만 한다. 환각 위험은 낮고 오매칭 위험이 남는다.

## 다음 단계

프론트 구현은 끝났습니다. 남은 것은 대부분 프론트 밖입니다(§13).

1. **서버측 운영 로그 적재를 확인합니다.** 프론트는 `POST /ai-consult/ask` 만 호출하고 로그에 관여하지 않으므로, 실제로 쌓이고 있는지 백엔드와 맞춰야 합니다.
2. **7-2의 로그 정책을 확정하고 약관·처리방침 수정을 법무에 요청합니다.** 대화가 서버에 남는다는 사실을 고지할지가 여기서 결정됩니다.
3. **QA 범위에 토스트 위치 변경을 포함합니다** — 전 페이지 영향입니다(로그인·마이페이지 저장·관심상품 등).
4. **프로모션 페이지를 데이터가 있는 환경에서 확인합니다** — ScrollToTop 스택이 모바일에서 화면 높이를 잡아먹지 않는지.
5. 로그가 쌓이면 Phase 3(§10)로 넘어가 7-3의 네 가지를 판단합니다.

**착수 전 확인으로 남겨둔 것**: 위젯·훅 네이밍을 `chatbot`(화면 용어)과 `ai-consult`(API 도메인) 중 하나로 통일할지(§7.3). 현재는 위젯은 `chatbot`, 서비스·훅은 `aiConsult` 로 갈라져 있습니다.
